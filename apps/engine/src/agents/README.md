# Hosted agents

This directory contains the hosted-agent catalog, protocol adapters, model discovery, conversation history, and handoff services.

Use `/model` in Jolo or `jolo agent list` to inspect configured agents. Hosted CLIs must already be installed and authenticated separately. User JSON manifests belong under `agents/` in the profile data directory; `catalog.js` reads them at engine startup and `manifests.js` defines the built-in defaults.

The usage ring in the desktop composer opens a panel with a tab per agent: the one answering, any called into the task, and every installed agent that can report its plan. For Claude Code, Codex and Antigravity CLI the tab also shows the signed-in plan's usage windows (for example the five-hour and weekly limits) from `agent.limits`, which asks Claude's `get_usage` control request, Codex's `account/rateLimits/read` or Antigravity's `/usage` command; none spends a model request. An answer about the account is kept for a minute; a refusal, an error or a timeout is asked again next time.

Typing `/` as the whole message in the desktop composer lists the answering agent's slash commands, read in the same `agent.models` probe as its models: Claude Code names its built-ins, plugins, skills and user-defined commands in its `initialize` reply (`commands: [{ name, description, argumentHint }]`), and Codex has no such list over its app-server, so it gets `/compact` and `/review`, the two its protocol has methods for, followed by its enabled skills from `skills/list`. A message that is a command, `/name` and its arguments with nothing before the slash, goes to Claude exactly as typed, without the shared-conversation handoff around it, since Claude takes a command only as the whole message. For Codex, `/compact` maps to `thread/compact/start` and `/review` to `review/start` (the words after it become a `custom` target, and with none Codex reviews the working tree; the findings are shown when its review mode ends); any other slash word goes to Codex as text.

Antigravity CLI (`agy`) answers through its print-mode stream, which has no channel for permission questions, so Jolo turns agy's own checks off and decides every tool call itself: agy's `PreToolUse` hook, loaded from a directory of Jolo's for the turn, hands each call to Jolo, and Jolo answers as it does for the other agents. Reads and edits pass inside the workspace and the turn's scratch directory and are refused outside them, `.git` included; commands and other tools need a grant or the user, through the same permission request. A refused call reaches agy as the reason, and agy carries on with its turn; a hook that fails or times out blocks the call. Its print mode takes text only, so a task with image attachments needs another agent, and it does not receive the `jolo` MCP server described below.

Hosted programs run with the local user's privileges. Jolo mediates the operations exposed by their transports; it does not sandbox arbitrary programs at the operating-system level. See the [security policy](../../../../SECURITY.md) and [CLI guide](../../../cli/README.md).

Claude Code gets one process per conversation, kept between turns (`claude-link.js`). Each run borrows it for a turn and gives it back, so background work Claude started (subagents, workflows, long commands) keeps running after the turn that started it; when that work finishes and Claude answers by itself, the answer arrives as a run of its own, marked as Claude carrying on. Stopping a run asks the process to interrupt its turn rather than killing it; a process that does not stop within a few seconds is closed. The process is started with `--replay-user-messages`, so it echoes each message as it takes it up: a run's answer is the result after its own echo, and a result before it ends a turn Claude began by itself. A background subagent that asks permission while the main thread is idle (its request names the subagent in `agent_id`) gets a run that ends once the request is answered; with no turn of the main thread in progress, stopping that run denies the request and never interrupts or kills the process. The process is closed when the task is archived or deleted, when its worktree is removed, when the model or effort changes (the next turn starts a fresh process that resumes the same Claude session), when the engine stops, and after thirty minutes without activity (`JOLO_HOSTED_IDLE_MS` overrides the wait). Its `jolo` MCP credential and scratch directory live as long as the process. Browser and delegation calls over that credential are served while a run of the conversation is in progress. An empty result Claude sends before any answer (it does this when it reports a task left over from an earlier process) is not taken as the end of the turn. Stop interrupts the process with `cancel_queued`, which ends the turn under way and drops whatever waits behind it. The background agents and workflows the process runs go on, listed in its activity (Jolo declares `perTaskStopAffordance` at `initialize`, so the interrupt spares them), until the person stops them: `session.stopTask` stops one with `stop_task`, and `session.stopBackground` stops them all, reporting how many ended within `STOP_TASK_GRACE_MS`; one that outlives it is left running and listed. Only a Claude Code that cannot stop tasks (it answers `not supported`) is interrupted instead, since its interrupt still ends background work. The person can also close the process themselves with `session.closeProcess` (the desktop's force-stop, offered when a stop left tasks running), which closes it in the same order as the closes listed above: its tasks are stopped with `stop_task` first, then its input is ended, and signals follow if it does not leave; any turn in progress ends with it. While the process reports background tasks running (`task_started` until `task_notification`), it counts as engine work: the engine does not idle out, reload or stop under it, and the idle close waits for it. A question asked while the main thread is not in a turn is background work's, whoever asks. The process traces every subagent to the main thread's Agent call it runs under, whichever run sees it start (from each subagent's `task_started` and its own messages, with `forwardNestedSubagentToolCalls` so a subagent's own subagents are reported too): a question under a running Agent call of the turn is the main thread's, any other is background work's, and "allow for this run" on background work's question covers that background work and the helpers it runs until the process closes. Background work that has just finished keeps the process counted as working until the turn reporting it begins. The other hosted transports still start a process per turn.

Each hosted turn receives a private scratch directory through `TMPDIR`, `TMP`, and `TEMP`, with instructions to use it for temporary files. Jolo's file permissions and the ACP file bridge allow that directory alongside the workspace; other temporary files remain outside the grant. Scratch files are removed when the turn completes or is cancelled. Finished mockups and visualizations belong in the workspace so their chat previews remain available.

Hosted CLI tools use the CLI's own execution timeouts by default, so long test suites, builds, and background jobs can continue. Jolo still enforces the turn's `budgets.maxActiveMs` (four hours by default), `maxIterations`, permissions, and cancellation. `budgets.toolDeadlineMs` applies to native Jolo tools and its browser bridge. To also limit blocking tools reported by a hosted CLI, set `budgets.hostedToolDeadlineMs` through `settings.update`; it defaults to `null` (disabled), including for existing profiles. Set it back to `null` to disable it. ACP and Codex command output continues streaming after the model resumes without consuming that optional tool deadline; a subsequent foreground wait gets its own deadline.

Ask in chat to use the inline browser, for example: “Open Google in the inline browser and search for iPhone 13 Pro Max.” The agent calls `browser_open` to open or reveal the workspace's **Browser** pane, then navigates and interacts with it. No manual Browser button click is needed. Native Jolo and hosted Codex, Claude Code, and ACP agents can list tabs, navigate, inspect accessibility snapshots, click, hover, type, fill or clear fields, select native options, press keys, scroll, go back/forward, reload, inspect network metadata, and capture screenshots. The workspace must be open in Jolo desktop; external Chrome/Edge windows are not controlled by this integration.

Hosted transports receive one `jolo` stdio MCP server per run. It always carries the schedule tools (`schedule_create` and friends, scoped to the run's own task), the search tool when the workspace index is enabled, and the browser tools when the engine supports them. Each browser call checks the workspace's live desktop connection. If desktop opens or reconnects during a turn, the agent can retry `browser_open` within that same turn. A missing host returns `browser_host_unavailable`. The credential is limited to the offered methods in the current run's workspace and is revoked when the run ends. Calls pass through Jolo's existing permissions, invocation records, deadlines, and browser broker. Screenshot results include MCP image content for the agent plus a stored artifact for Jolo's transcript. Raw CDP and arbitrary page JavaScript are not exposed. A page's content is data, not agent instructions.

Every chat transport receives Jolo's browser instructions on first and resumed turns: use the dedicated browser tools, never computer use or an external `iab` browser. Desktop run admission waits for its pane registration. Codex's extra approval for Jolo's own scoped MCP bridge is accepted for that call so the operation reaches Jolo's dispatcher; external-server questions and forms remain unaccepted.

Chat opens share the same workspace browse grant as the Browser button, without a separate consent dialog; see the [inline browser security policy](../../../../SECURITY.md#inline-browser-control). An agent cannot replace another workspace's open browser. It receives a busy error until the user closes or explicitly switches that browser.

The host serializes operations per tab and expires element references after navigation. Use the refs returned by `browser_snapshot`; use `tabId` from `browser_tabs` when several tabs are attached. Closing the pane or cancelling the run stops pending browser input. Run `bun run desktop:smoke --browser-chat` to verify that chat opens a closed browser pane and controls its page, or `bun run desktop:browser-smoke` to check the individual controls against local Chromium pages. The hosted MCP path is covered by the integration tests. For an explicit live-agent check using its installed CLI and existing login, run `bun run desktop:smoke --real-browser-agent codex` (or `claude` / `grok`); this uses the agent's account against a disposable local page and checks both first and resumed turns.
